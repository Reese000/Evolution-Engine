## 1. Architecture Map

### System Overview

Evolution Engine is a self-evolving RV32I machine-code AI. It maintains a champion program, mutates it to create challengers, evaluates them on a VM, and retrans a transformer model on champion traces. The system is orchestrated by a meta-controller that tunes hyperparameters across cycles.

### Data Flow Per Cycle

```
1. run_multi_cycle.py / autonomous_runner.py starts cycle N
2. MetaController.tune_retrain_params() → LR, freeze layers, etc.
3. EvolutionEngine.run(num_generations):
   a. For each generation:
      - _generate_challengers() → mutations of champion
      - _evaluate_batch() → VM evaluation (CPU/GPU)
      - batch_compute_fitness() → multi-signal scoring
      - _select_elite() → tournament + QD selection
      - _update_champion() → verify gate → promote if better
      - _update_qd_archive(), _update_novelty_archive()
   b. _try_recurrent_feedback() → save champion traces
   c. _try_curriculum_advance() → check if stalled → advance level
4. MetaController.update_cycle() → record telemetry
5. MetaController.accept_checkpoint() → gate model checkpoint
6. Training pipeline (train_model.py):
   a. load_champion_traces() from recurrent_data.jsonl
   b. augment (register rename, synthetic, reference solutions)
   c. pack sequences → DataLoader
   d. Fine-tune transformer (position-aware weighted CE loss)
   e. Checkpoint gating: only accept if val_loss improves
7. Log cycle results, prune old cycle directories
```

## 5. Gaps

### 5.1 L4 Plateau Analysis

**Current state** (from meta_controller_state.json):
- Best fitness: 356.99
- Best level: 4 (stuck for 3+ cycles)
- Best val_loss: 0.2024
- Diversity: 0.3 (constant — diversity not improving)

**Root cause analysis:**

1. **Binary verify at L4** (`tasks_rv32i.py:313-318`): Level4.verify() returns 1.0 only if ALL registers 3-7 match exactly. This is a binary gate — there's no partial credit. The champion can have reg_match=0.8 (4/5 registers correct) but verify() returns 0.0.

2. **Partial verify fix (commit 5f04101)**: Added partial verify scoring so that when verify_score > 0, the champion can be replaced with a gradient signal. However:
   - The L4 verify is still binary (0.0 or 1.0) — there IS no "partial" for L4 since all 5 registers must be exact
   - The `_champion_partial_verify` attribute is set but doesn't change the verify() behavior
   - The real gap: L4 requires computing `x7 = x4 + x6` where `x4 = 2*x3` and `x6 = memory_load(2048)`. This requires BOTH multiplication (SLLI) AND memory operations, which the model hasn't learned yet.

3. **Curriculum stall threshold**: `curriculum_stall_threshold = 3` means after 3 generations without improvement, the engine tries to advance. But L4 verify requires passing ALL 5 registers, which requires the champion to solve a multi-step computation (LUI → SLLI → ADD → LW → ADD → ADD → EBREAK). The model-generated programs are not reaching this complexity.

4. **Fitness gradient weakness**: The `level_bonus = champion_level * 25.0` means L4 gets 100 points. But the `solved_bonus = 50.0` only triggers at reg_match ≥ 0.99. Programs at L4 that get 4/5 registers right get reg_match=0.8 but no solved_bonus and no verify pass. The fitness gradient between "almost solving" and "solving" is too steep.

5. **Partial verify scoring interaction**: At `_compute_fitness()` line 2940, `_partial_v` is used but only in the context of the champion's existing score. Since L4 verify() returns 0.0 (no partial credit possible), the partial verify score is always 0.0 at L4, making the fix ineffective for this specific level.

### 5.2 Partial Verify Gaps

The partial verify scoring (commit 5f04101) has these gaps:

1. ~~**L4 verify is inherently binary** (`tasks_rv32i.py:313-318`): Returns 0.0 or 1.0 with no intermediate values.~~ ✅ Fixed — All verify() methods now return continuous scores via `_continuous_verify(output, inst, reg_list)` helper.

2. **Verify vs fitness disconnect**: `_verify_champion()` (line 5127) stores partial_verify score, but `_compute_fitness()` doesn't use it as a direct fitness modifier — it's only stored for future reference.

3. **Champion replacement gating**: At line 4941, if `verify_score > 0.0` the replacement is allowed. But for L4, verify_score is either 0.0 or 1.0, so the "partial" path is never taken.

### 5.3 Training Bottlenecks

1. **Val loss trajectory**: From meta_controller_state.json, val_loss went 0.26 → 0.2024 → 0.2048 → 0.2041 → 0.2124. This is essentially flat — the model is not learning from new traces because the champion isn't progressing.

2. **Trace quality**: Champion traces are only saved when fitness > MIN_FITNESS_FOR_TRACE (0.1). At L4, if the champion doesn't solve the task, traces may not contain the right instruction patterns for the model to learn the missing computation.

3. **Training data distribution**: The model was trained on L0-L3 traces (simpler programs). L4 requires a qualitatively new pattern (memory load + arithmetic chain). The training data distribution shift is too large for the current augmentation pipeline.

4. **LR cap issue**: The README notes "LR cap prevents learning rate from growing unboundedly" — this was merged but the meta_controller's `tune_retrain_params()` already has lr_min/lr_max bounds (1e-6 to 3e-4). The issue is that even with bounded LR, the model's gradient signal from L0-L3 traces doesn't help it learn L4 patterns.

### 5.4 Architecture Concerns

1. **evolution_engine.py is a 6175-line monolith**: Contains VMFarm, HallOfFame, EvolutionConfig, and EvolutionEngine in a single file. The `run()` method is 271 lines, `_compute_fitness()` is 344 lines, `_choose_mutation_strategy()` is 267 lines.

2. **Module count explosion**: 156 test files with wave-based naming (wave1-wave78 × final/smoke). Many appear to be incremental additions from adversarial audits rather than systematic test organization.

3. **Import path hacks**: Multiple files use `sys.path.insert(0, ...)` for relative imports. `paths.py` provides `ensure_project_on_path()` but it's called inconsistently.

## 6. Priority Issues

### P0 — Critical (Blocks correctness or data integrity)

#### P0-1: Batch vs Individual Fitness Divergence
- **Evidence:** `tests/test_batch_evaluation.py` — 3 tests failing with fitness divergence of 20-35 points
- **Root cause:** `_champion_partial_verify` state mutation during batch evaluation creates different fitness scores than individual evaluation
- **Files:** `evolution_engine.py:2940` (partial verify in fitness), `evolution_engine.py:4947` (partial verify storage)
- **Impact:** Batch evaluation (used in production) produces different fitness scores than individual evaluation (used in tests). This means champion replacement decisions may differ between test and production contexts.

#### P0-2: ~~L4 Verify is Binary, Partial Verify Ineffective~~ ✅ FIXED
- **Evidence:** `tasks_rv32i.py:313-318` — L4.verify() returned 0.0 or 1.0 only
- **Root cause:** The partial verify scoring system (commit 5f04101) assumes verify() can return continuous scores. L4's verify was all-or-nothing.
- **Files:** `tasks_rv32i.py` (all 34 verify methods + `_continuous_verify` helper)
- **Impact:** The L4 plateau escape mechanism doesn't work for L4 because the verify function has no gradient signal. The champion can never be replaced with a "partial" improvement.
- **Fix:** Added `_continuous_verify()` helper that returns `n_correct_regs / total_regs`. All 34 verify() methods (L0-L30 + BitwiseTask, ArithmeticTask, MemoryAccessTask) now use this helper, returning continuous scores [0.0, 1.0]. Tests: 41/41 passing.

- **Evidence:** README says "12-level curriculum" but `tasks_rv32i.py` defines 31 levels (L0-L30)
- **Files:** `README.md` (curriculum section), `tasks_rv32i.py:2386-2418` (LEVELS dict)
